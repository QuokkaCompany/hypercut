# 편집 화면 재사용 — 두 후보 모두 반복 메모리 목표 실패

2026-09-06. [1,000컷 기준 측정](2026-09-06-thousand-cut-performance-results.md)의 브라우저 RSS 2.050GiB 실패에 대해 [개선 계획](../plans/2026-09-06-editor-render-memory-plan.md)을 적용했다. 컷 목록을 메모화하고 타임라인의 파형·눈금·컷 요소를 재사용한다. 재생 위치, 선택, 컷 변경, 현재 원본/편집본 시간축, 작업 잠금 상태는 해당 데이터가 바뀔 때 갱신한다. 첫 후보의 60분 브라우저 3회 중 세 번째 RSS가 2.172GiB로 실패했다. 아래 기능 회귀는 첫 후보의 결과이며 두 번째 후보의 완료 근거로 합산하지 않는다.

전용 검사는 고정 컷 `[2,4), [8,10)`을 가진 16초 영상에서 원본 7.5초 선택이 편집 영상의 5.5초로 이동하는지, 첫 컷을 복원하고 다시 렌더하면 7.5초로 이동하는지 확인했다. 다른 세 컷 프로젝트로 교체한 뒤 원본 11.5초가 새 편집 영상 8.5초로 이동하는지도 검사했다. 재생 뒤 선택, 실행 취소/다시 실행, 타임라인 확대·선택, 작업 중 버튼 잠금/해제, 저장한 전체 컷 상태와 원본 해시를 확인했다. Chrome/Mac 실행 화면도 열어 검토했다.

새 테스트의 첫 실행은 저장 스키마가 붙이는 `reason: silence`를 정답에서 생략해 마지막 비교에서 실패했다. 입력 정답에 해당 필드를 명시한 뒤 두 앱이 통과했다. 앞선 시각·복원 단계는 이미 통과했고 제품 코드는 이 시험 보정으로 바꾸지 않았다. 실패 기록·시험 코드·화면은 `test-output/editor-render-candidate-e2e/`, 정식 기능 결과는 `test-output/editor-render-candidate-e2e-v2/`에 보존했다.

## 첫 후보 성능 비교

동일한 `scripts/threshold-benchmark.mjs`와 입력 해시로 Chrome 60분 3회를 완료했다. [원시 결과](results/2026-09-06-editor-render-browser-long.json)와 [전체 데이터/메모리 감사](results/2026-09-06-editor-render-audit.json)를 보존한다. 원시 경로는 `test-output/editor-render-performance/browser-long/`이다. 데이터·인코더 스레드 수·코덱·해상도·CRF·프리셋을 변경하지 않았다. 3회 모두 기준의 전체 분석·저장 프로젝트(저장 시각 제외)와 일치했고, 출력 MP4도 실제 파일 SHA-256이 같았다. 그러나 최대 RSS는 1.872 → 1.950 → 2.172GiB로 증가했다. 출력 중앙값은 141.256초, 최대 141.602초였고 시간·조작·싱크·취소/재시도는 통과했다. 전체 메모리 개선 성공으로 판정하지 않는다.

세 번째 출력 피크에서 화면 렌더러는 약 599MiB였다. 각 UI 단계 피크도 약 551 → 562 → 594MiB였다. 메모화한 목록이라도 컷 하나가 변경되면 내부 1,000개 행과 아이콘이 다시 구성되는 코드가 남아 있었다. 이 관측만으로 메모리 누수를 단정하지 않는다.

시험 시 코드 기준은 `b6a161e`이며 UI 변경은 작업 트리에 있었다. `test-output/editor-render-performance/source-manifest.json`에 새 `CutList`, `App`, `Timeline`, 실제 브라우저 번들, 서버·시험 코드·Mac 패키지 SHA-256을 별도로 기록했다. 미디어 시험과 빌드는 동시에 실행하지 않는다.

Chrome 3회 성능 통과 후에만 나머지 10분/60분 두 앱 조건을 확인한다. 실제 한국어 발화 품질·작업 시간 절감·cold-cache·긴 자막/효과음 동시 합성·인증된 AI 연결은 이 변경의 기능 검사로 통과 처리하지 않는다.

## 두 번째 후보

변하지 않은 개별 컷 행을 재사용하고, 클릭/키보드 이벤트는 목록에서 현재 콜백으로 처리한다. 파형·눈금 배경도 컷 표식과 분리해 컷 변경 때 재구성하지 않는다. 모든 컷과 기존 버튼·스크롤·시간축 계약은 유지한다. 첫 후보 소스는 `test-output/editor-render-performance/candidate-v1/`에 보존했다. 단위 75개와 타입/빌드/패키징을 다시 통과했다. 새 브라우저 실행 번들은 `index-4MyEqYPb.js`다.

- [현재 컷·시간축·키보드 검사](results/2026-09-06-editor-render-row-e2e.json): 두 앱 2회 PASS. Space/Enter로 복원·제거하는 동작도 확인했다.
- [일반 편집 회귀](results/2026-09-06-editor-render-row-regressions.json): 두 앱 2회 PASS. 같은 기록의 프로젝트 검사는 다음 8조건과 중복 집계하지 않는다.
- [프로젝트 읽기/저장 경합](results/2026-09-06-editor-render-row-project-io.json): 두 앱 8조건 PASS.

합계 12개의 실제 UI 실행/조건을 새 후보에서 확인했다. 첫 후보의 작업 경합 34조건과 효과음 교차 8조건을 두 번째 후보에서 다시 실행한 것으로 집계하지 않는다. 두 번째 후보는 개별 행과 타임라인 배경만 추가 변경했으며 현재 App의 저장/작업 상태 코드는 첫 후보와 같다.

[실제 소스·번들·패키지 해시](results/2026-09-06-editor-render-row-source.json)를 고정한 뒤 `test-output/editor-render-row-performance/browser-long/`에서 Chrome 60분 3회를 완료했다. [측정 결과](results/2026-09-06-editor-render-row-browser-long.json)와 [원시 데이터 감사](results/2026-09-06-editor-render-row-audit.json)를 보존한다. 기능 검사 당시의 Mac 화면도 열어 목록·선택 표시와 레이아웃을 확인했다.

| 반복 | 분석 시간 | 출력 시간 | 합산 RSS 최대 | 판정 |
| --- | --- | --- | --- | --- |
| 1 | 37.362초 | 142.123초 | 1.860GiB | 측정 목표 PASS |
| 2 | 37.381초 | 141.570초 | 1.924GiB | 측정 목표 PASS |
| 3 | 37.421초 | 141.682초 | 2.145GiB | 메모리 FAIL |

3회 모두 전체 분석 데이터와 저장 프로젝트(저장 시각 제외)가 기준 실행과 같고, 저장한 MP4의 실제 SHA-256도 기준 출력과 같다. 전체 디코딩과 18쌍의 독립 영상·음성 표식 검사를 통과했다. UI 동작군별 최대 p95는 115.449ms다. 실제 작업 중 취소는 표시 1ms, 재시도 가능 상태까지 314.676ms였고 프로젝트 보존과 다음 반복의 완료를 확인했다. 취소 시점은 PCM 분석 초기이며 중간 구간의 취소 시험으로 표현하지 않는다. RSS 표본 간 최대 간격은 295.465ms였다.

세 번째 출력 피크에서 가장 큰 화면 렌더러는 587.94MiB, FFmpeg는 390.28MiB, 서버는 242.31MiB였다. 첫 번째 출력 피크의 같은 항목은 각각 333.08MiB, 405.11MiB, 209.13MiB다. 첫 두 회의 낮은 값만으로 메모리 개선 성공을 주장하지 않는다. 다른 Chrome 자식 프로세스도 합산 RSS에 포함했다.

두 번째 후보도 메모리 목표에 실패했으므로 남은 9회의 성능 검사는 시작하지 않았다. 소스는 `test-output/editor-render-row-performance/candidate-v2/`에 보존했다. 다음은 [진단 계획](../plans/2026-09-06-editor-render-memory-plan.md)에 따라 반복 조작 중 DOM·이벤트 리스너·JavaScript 힙과 프로세스 RSS를 구분해 측정한다. 정식 성능 기준과 시험 조건은 변경하지 않았다.

## UI 반복 조작의 메모리 진단

`scripts/editor-memory-diagnostic.mjs`로 별도 Chrome 앱을 실행해 같은 60분 영상을 한 번 가져오고 분석했다. 이후 복원/실행 취소·설정·재생/정지를 각각 32회씩, 세 주기 수행해 총 288회 조작을 확인했다. 반복 가져오기·출력은 수행하지 않았고 강제 GC도 호출하지 않았다. [진단 결과](results/2026-09-06-editor-memory-diagnostic.json)와 [소스/원시 RSS 감사](results/2026-09-06-editor-memory-diagnostic-audit.json)를 보존한다. 원시 RSS와 실행한 시험 코드는 `test-output/editor-memory-diagnostic-row-v1/`에 있다.

- 첫 복원 묶음 이후 마지막 유휴 상태까지 실제 화면 요소는 11,962개, 컷 행은 1,000개로 일정했다. 삭제 상태도 매 묶음 끝에 원래대로 복구됐다.
- 각 주기의 재생 조작 후 JavaScript 사용 힙은 19.240 → 10.599 → 29.325MiB였다. 마지막 5초 유휴 후 사용 힙은 29.331MiB, 확보된 전체 힙은 76.250MiB였다. 이벤트 리스너 수도 조작 중 증가했다가 감소해 단조 증가 형태는 아니었다.
- 프로세스 합산 RSS 최대는 1.673GiB, 마지막 표본의 가장 큰 렌더러는 543.47MiB였다. 전체 352개 RSS 표본에서 오류가 없었고 최대 간격은 276.746ms였다. 앱 오류·외부 요청·원본 변경은 없었다.

이 한 번의 진단은 DOM이나 JavaScript 힙 누수의 확정 근거가 아니다. 렌더러 RSS와 JavaScript 힙 사용량은 같은 지표가 아니며, CDP·Playwright 측정 비용도 포함된다. 출력 단계가 없는 이번 진단의 2GiB 미만 값을 정식 반복 성능 통과로 대신하지 않는다. 다음 진단에서는 미디어 재생 및 자동화 조작의 비용을 분리하고, 필요하면 반복 가져오기·출력 단계에서 추가되는 자원 수명을 추적한다. 현재 반복 메모리 실패는 미해결이다.
