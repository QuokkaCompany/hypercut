# 반복 출력의 영상 인코딩 동시 처리 제한

2026-09-06. 긴 목록 후보 `3d572b4`는 60분 세 번째 반복의 합산 RSS가 2.008GiB로 실패했다. 세 번 모두 메모리 최고점은 출력 단계였고 당시 FFmpeg는 약 343~348MiB였다. 서버와 브라우저 렌더러의 반복 증가도 관측했으므로 이를 모두 인코더 누수로 설명하지 않는다.

## 이번 후보

영상 인코더의 최대 스레드를 4개에서 2개로 줄이는 후보를 비교한다. 현재 CRF 18, veryfast 프리셋, 해상도·프레임·컷·자막·효과음·AAC 조건을 유지한다. 미리보기의 CRF 25/ultrafast도 유지한다. 자막 유무와 관계없이 출력 인코더에 같은 최대값을 적용하며, CPU가 하나이면 기존처럼 하나만 쓴다. UI나 파일 형식·지원 범위는 바꾸지 않는다.

[FFmpeg 공식 문서](https://ffmpeg.org/ffmpeg-codecs.html#libx264_002c-libx264rgb)는 인코딩 스레드 수와 CRF를 별도 옵션으로 정의한다. 스레드 수 변경만으로 모든 영상의 픽셀·비트스트림 동일성을 보장하지 않는다. 이전 60초 진단에서도 2개 스레드는 동일한 합성 정답과 샘플 픽셀을 유지했지만 MP4 바이트가 달랐다. 이번 후보는 전체 프레임을 확인하고 실제 출력 속도 증가도 보고한다.

## 검증 순서와 기준

1. 현재 버전과 2개 스레드 후보를 동일 60초 백엔드 합성으로 순차 비교한다. 프로세스 트리 RSS, 합성·앱 검증 시간, 전체 프레임 수/PTS·자막/효과음·싱크·SRT 정답과 출력 해시를 보존한다. 서로 다른 비트스트림의 디코딩 프레임도 전체 비교한다.
2. 미디어·프레임 경계·호환성·자막·효과음 통합과 단위를 검사한다. 단순한 스레드 인자 복사 테스트 대신 실제 출력 검사를 사용한다. 타입/빌드·Mac 패키징 후 두 앱의 60초 전체 합성·저장·취소·재시도를 확인한다.
3. 후보를 커밋으로 고정하고 브라우저 60분 3회를 같은 앱에서 수행한다. 분석 ≤영상 길이의 20%, 출력 ≤영상 길이, 합산 RSS ≤2GiB, 조작군 p95 ≤200ms, 취소 표시 ≤300ms/재시도 ≤5초를 유지한다. 완결한 실행이 실패하면 다른 장시간 조건으로 확대하지 않는다.
4. 통과하면 10분/60분 × 두 앱의 남은 반복으로 진행한다. 파일 캐시 없는 조건과 실제 한국어 발화·전사·시간 절감·인증 AI·Mac OS 네트워크 차단은 각각 별도 증거를 확보한다.

무음 편집·자막·효과음의 품질 목표는 기존 계획을 따른다. 스레드 수를 줄여도 반복 메모리 문제가 남으면 실패로 보존하고, 서버/브라우저 자원 수명을 별도로 조사한다. 강제 GC, 브라우저 기능 차단, 메모리 기준 완화는 이 후보에 포함하지 않는다.
